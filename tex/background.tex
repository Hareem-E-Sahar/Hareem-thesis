\section{Empirical Software Engineering}
Empirical Software Engineering (ESE) is the study of software and its development in an empirical way using the real-world data~\cite{kitchenham2008evaluating}. Instead of relying purely on theoretical models, ESE draws on the wealth of information stored in software repositories, such as version control histories, issue trackers, discussion forums~\cite{chatterjee2020software}, and source code, to understand how software evolves, how developers work, and what factors influence software quality, cost, and maintenance.

With the rise of platforms like GitHub and GitLab, there is a vast amount of publicly available software artifacts and rich metadata about the development processes including source code, bug reports~\cite{bettenburg2008makes}, commit messages, developer discussions~\cite{ehsan2020empirical,venkatesh2016client}, and release histories. These artifacts offer valuable insights that can inform the design of developer assistance tools~\cite{hassan2006mining} and support evidence-based decision making in software engineering (SE). 
 
 
A key venue dedicated to this line of work is the Mining Software Repositories (MSR) conference\footnote{https://conf.researchr.org/series/msr}, which brings together researchers focused on analyzing data from software repositories to tackle real-world problems in development and maintenance. One particularly active area is mining bug reports form bug repositories. Analyzing bug reports has proven useful for tasks such as bug triaging~\cite{hu2014effective}, fault localization, and predicting future defects~\cite{li2018progress}(an area known as Software Defect Prediction (SDP)). 

%Key goals of ESE include identifying best practices, evaluating the effectiveness and efficiency of development methodologies (e.g., Agile, DevOps), measuring software quality attributes (such as maintainability or testability), and understanding human and organizational factors in software teams. The field often employs both qualitative and quantitative research technique.

Empirical studies in SE often adopt well-established research methods such as case studies, surveys, experiments, and observational analyses~\cite{kitchenham2008evaluating}. These methods help explore questions ranging from how developers collaborate, to what makes code more prone to bugs, to whether certain practices improve productivity or code quality. Broadly, these efforts can be categorized as exploratory (understanding phenomena), explanatory (explaining relationships), or technical validation (evaluating tools and techniques)~\cite{kitchenham2008evaluating}. %%Together, these methods ensure that conclusions about software processes, methods, and tools are grounded in real-world data and statistically sound analysis, ultimately improving practice of software development and making software more reliable and maintainable.

In this thesis, we approach software defect prediction as a retrieval problem: predicting whether a change is defective and explaining its prediction by comparing it against what has been seen before. This section introduces the conceptual foundation for this approach and explains how source code's similarity with natural language (NL) makes text-retrieval techniques applicable to it. It then surveys how Information Retrieval (IR) has been used in software engineering, from classical term-matching models to neural, embedding-based methods. Section~\ref{sec:representations} and Section~\ref{sec:similarity} detail, respectively, how code is represented and how those representations are compared. Both are the technical building blocks that make the IR perspective introduced here operational.

\subsection{Code as Natural Language}
\label{sec:code-as-nl}
Source code is a formal artifact as it has to satisfy a strict grammar. Also it compiles to well-defined behavior, unlike the natural language text that does not follow any such rules. Hindle et al.~\cite{hindle2012} challenged this assumption and showed that source code written by humans is highly repetitive and predictable at the statistical level comparable to, and in some corpora more repetitive than, natural language text. Using n-gram language models trained on large code corpora, they found that code exhibits the same kind of local, learnable regularities that make natural language amenable to statistical modeling.

This finding, often called the naturalness hypothesis, reframed source code as a textual artifact that could be analyzed with the same tools developed for natural language: tokenization, term weighting, language modeling, and retrieval. It underlies the token-based representations introduced in Section~\ref{sec:representations}. Information Retrieval techniques were originally designed for natural language documents; the naturalness hypothesis is what justifies applying them directly to source code and to other software artifacts such as bug reports and commit messages.


\subsection{Information Retrieval Foundations}
\label{sec:ir-foundations}
Information Retrieval is the problem of identifying documents relevant to a query within a large collection of unstructured documents. Classical IR models fall into two broad families: vector space models such as TF-IDF, which represent documents and queries as weighted term vectors, and probabilistic models such as BM25, which rank documents by the estimated probability of relevance. Both were developed for natural language document collections rather than for software artifacts.

Any IR system, classical or neural, depends on two components: a representation of the documents and query being compared, and a similarity or relevance measure defined over those representations. Section~\ref{sec:representations} discusses how source code and related artifacts are represented, from lexical tokens to syntax trees to learned embeddings. Section~\ref{sec:similarity} details the corresponding similarity measures, including the full formulation of TF-IDF and BM25. 

\subsection{Information Retrieval in Software Engineering}
\label{sec:ir-in-se}


IR has been applied to a range of SE tasks, including code search, bug localization, and crash report de-duplication~\cite{campbell2016unreasonable}.

In bug localization, IR techniques generate a ranked list of potentially defective files for a developer to inspect, given a bug report. Locus~\cite{wen2016locus}, for example, measures relevance between bug reports and software changes, and successfully locates the bug-inducing change within the top five results for 41.0\% of bugs. Such models reduce the search space substantially, though developers must still inspect the ranked candidates themselves. A related use case is duplicate bug report detection. TF-IDF and cosine similarity have been used to identify duplicate reports in real time by comparing incoming reports against the issue tracker before submission~\cite{hindle2019query}, reducing redundancy in bug databases.


In code search, developers typically write natural language queries to locate relevant code snippets. Because TF-IDF-based retrieval relies on shared vocabulary between query and document, it performs well only when developers describe code using the same term the code itself uses. In practice this is often not the case because developers frequently describe what code does using terms different from the identifiers, comments, or structure of the code itself. This is known as vocabulary mismatch problem. Lu et al.~\cite{lu2015query} addressed this issue through query expansion whereby queries were enriched with synonyms drawn from WordNet, a lexical database of English, before matching them against source code identifiers. FaCOY~\cite{facoy} took a different route, using Q\&A platforms such as Stack Overflow to generate alternate phrasings of a query, which improved its ability to identify semantically equivalent code clones.

\subsection{Limitations of Embedding-Based Methods}
\label{sec:embedding-limitations}
These gains come with limitations that matter for this thesis~[42]. Embedding-based methods do not explicitly model the hierarchical structure of source code~\cite{alon2019code2vec}, i.e., the relationships between statements, control flow, and functions that are often essential for understanding what a change does.

Embeddings are also dense, distributed representations, so the individual dimensions of an embedding vector carry no interpretable meaning on their own~\cite{grattan2024need} This opacity is a direct obstacle for software defect prediction, where developers need transparent, actionable reasons for why a change is flagged as risky, not just a prediction~\cite{ribeiro2016should}. Embeddings offer no traceable features behind a prediction~\cite{allamanis2014learning}, and they do not explicitly capture the hierarchical relationships between code elements that are often central to identifying defects~\cite{allamanis2014learning}. For a task where explainability and structural understanding are essential, not an afterthought, embeddings are unsuitable.

For this reason, in this thesis we do not adopt embeddings as our default representation. Instead, we build on the theoretically well-established, simpler alternatives detailed in the next two sections: TF-IDF for textual similarity and tree kernels for structural similarity. These let us construct software defect prediction models that are explainable by design and that retain the hierarchical structure of source code that embeddings discard.

\subsection{Lexical and Token-Based Representations}
A common approach to deal with raw source code is to convert it into a sequence of lexical tokens (e.g., keywords, operators, identifiers) using a tokenization method. Token-based models, such as bag-of-words (BoW), Term Frequency Inverse Document Frequency (TF-IDF), or n-gram models~\cite{hindle2012} capture lexical regularities and token frequencies making them appropriate for tasks such as bug de-duplication~\cite{campbell2016unreasonable} and code search based on natural language queries~\cite{lu2015query}. These representations form the basis of traditional information retrieval (IR) methods and are used in defect prediction models~\cite{yan2020JIT, pornprasit2021jitline} due to their simplicity and computational efficiency. Token-based representations, however, cannot capture the syntactic and semantic relationships between program elements, which limits their effectiveness for tasks that require reasoning beyond surface-level token overlap. These limitations motivate the use of richer representations that explicitly encode program structure.

\subsection{Syntactic Representations}
To capture the structure of a program, syntactic representations such as Abstract Syntax Trees (ASTs) and Concrete Syntax Trees (CSTs) are used. ASTs encode the hierarchical structure of programs by representing code as a tree, where each node corresponds to a language construct such as a method, loop, or variable declaration~\cite{neamtiu2005understanding}. This structure enables the extraction of rich syntactic features, that reflect the program's hierarchical organization, making ASTs effective for tree-based similarity measures such as tree kernels and subtree matching~\cite{tufano2018deep}. Such representations can benefit tasks like clone detection~\cite{deckard2007}, where structural similarities indicate potential code duplication or reuse. However, ASTs do not explicitly encode program semantics, which limits their ability to identify semantically equivalent code.

\subsection{Semantic Representations} 
Semantic representations~\cite{efstathiou2019semantic} focus on modeling relationships that reflect program behavior rather than code structure alone. They encode how program elements interact or depend on one another, providing a higher-level view of program functionality. Earlier semantic representations included graph-based models such as program dependence graphs (PDGs~\cite{komondoor2001using}) and data-flow graphs (DFGs), which encode control and data dependencies explicitly. Recent ones are derived from neural language models pre-trained on a large corpus of source code. %Modern graph-based embeddings can be seen as a learned extension of these approaches.

\subsection{Textual Similarity}
\textbf{\textit{Textual similarity}} approaches often use Term Frequency-Inverse Document Frequency (TF-IDF)~\cite{salton1978term}, where Term Frequency (TF) measures how often a term appears in a specific document (e.g. a code segment), and Inverse Document Frequency (IDF), measures how rare/discriminative the term is across all documents. Together, TF-IDF highlights the frequently occurring terms in one document but uncommon in others. Cosine similarity is then used to compare TF-IDF vectors by measuring the angle between them. A smaller angle means the documents are more similar in content. Longer documents containing more terms can be favored by TF-IDF. 

BM25 algorithm~\cite{BM25} improves upon TF-IDF~\cite{salton1978term} by modeling term importance differently. It normalizes the term frequency by introducing a saturation function which ensures that the impact of a term does not increase linearly with frequency. It further incorporates document length normalization to prevent longer code segments from being unfairly penalized or favored. These adjustments can provide more effective relevance scoring across documents of varying lengths and content, making BM25 a robust alternative to traditional TF-IDF-based cosine similarity in many retrieval settings.
Given a query document Q, containing keywords \(q_1, \ldots, q_n\), the BM25 score between the Q and document D is:

\[
\text{score}(D,Q) =
\sum_{i=1}^{n}
\text{IDF}(q_i)\cdot
\frac{f(q_i,D)\cdot (k_1+1)}
{f(q_i,D) + k_1\cdot\left(1 - b + b\cdot\frac{|D|}{\text{avgdl}}\right)}
\]

where \(f(q_i,D)\) is the number of times the keyword \(q_{i}\) appears in the document D, \(|D|\) is the length of the document D in words, and \(avgdl\) is the average length of document in the documents corpus.  
\(k_1\) and b are free parameters, usually chosen, in absence of an advanced optimization, as 
\(k_1 \epsilon [1.2,2.0]\) and \(b=0.75\). \({IDF}(q_i)\)
is the IDF weight of the query term 
\(q_i\). The definition of IDF is as follows:
\[
\text{IDF}(q_i) = \ln\left(\frac{N - n(q_i) + 0.5}{n(q_i) + 0.5} + 1\right)
\]

where N is the total number of documents in the collection, and 
\(n(q_i)\) is the number of documents containing \(q_{i}\).

\subsection{Structural Similarity} \textbf{\textit{Structural similarity}} methods use program representations such as ASTs to capture syntactic relationships encoded in program structure. These methods compared code based on tree structure rather than directly comparing sequences of tokens. Techniques like tree edit distance~\cite{song2024revisiting} compute similarity by measuring the minimum number of edit operations (insertions, deletions, or modifications) needed to transform one tree into another~\cite{phan2018automatically}. An alternative is provided by tree kernels, which quantify structural similarity based on shared substructures between trees. Tree kernels implicitly represent trees through their constituent substructures, enabling structural information to be incorporated into similarity computation without explicitly enumerating the resulting feature space~\cite{treekernels2001}.

\textit{\textbf{Tree kernels}} provide a method of computing similarity between tree-structured data without explicitly enumerating all possible subtrees. By comparing parts of trees and finding shared sub-parts, tree kernels can help identify recurring structural patterns in data. For example, in NLP~\cite{STKoptimal}, tree kernels can help identify noun or verb phrases by comparing the syntactic trees of different sentences. In bioinformatics~\cite{vert2002tree}, they are used to compare phylogenetic trees to identify shared evolutionary patterns. Similarly, given a set of ASTs representing the syntactic structure of source code, tree kernels can identify syntactic patterns, e.g., loops, method calls, that recur across different code fragments.

\section{Software Defect Prediction}
A software defect, also known as a bug, fault, or error, is a deviation from the expected software behavior. Defects cost the US economy an estimated \$2.41 trillion in losses\footnote{https://www.it-cisq.org/the-cost-of-poor-quality-software-in-the-us-a-2022-report/} in $2022$. To prevent these defects and improve software quality, organizations regularly conduct code testing and inspections. Such activities are costly and resource-intensive~\cite{thongtanunam2015investigating}, making it impractical to thoroughly examine every part of a large system. 

Software Defect Prediction (SDP) addresses this challenge by identifying software modules (files, classes, or methods) that are most likely to contain defects. By prioritizing these high-risk areas, developers can allocate testing and quality assurance resources more efficiently. Traditional SDP models used project's historical snapshots and defect data from past releases to predict which modules are likely to be defective in future versions. 

Such data includes historical defects, code metrics (e.g., lines of code, McCabe's cyclomatic complexity, coupling between objects)~\cite{ck1994,martin1994} or process metrics (e.g., code churn, number of revisions, number of bug-fixing commits, and developer activity)~\cite{nagappan2005} etc. Models are trained in a supervised manner using classifiers such as Decision Trees, Naive Bayes, Logistic Regression, Bayesian Networks, and Support Vector Machines~\cite{lessmann2008bench}. Evaluation is conducted on publicly available defect datasets such as the NASA MDP~\cite{gray2012reflections} and Jureczko datasets~\cite{Jureckzo}.

Constructing such datasets requires identifying which parts of the software were responsible for introducing past defects. This process is commonly performed using the SZZ algorithm, which links bug-fixing commits to the changes that originally introduced the defects.


\subsection{Defect Labeling using SZZ Algorithm}
Version Control Systems (VCS) contain valuable historical information about known software defects and the source code changes made to fix those defects. This information can be systematically extracted and used to support empirical software engineering research, including software defect prediction.

When developers push their changes from the local machines to the central repository, each set becomes a commit identified by a unique commit hash. Alongside the code, developers typically include a commit message describing the intent or purpose of the change.
 

When fixing bugs, developers often reference the related issue numbers or describe the bug fix directly in their commit messages. Such references allow us to identify bug-fixing commits. Once a bug-fixing commit is identified, we can trace back through the project's history to find the commit that introduced the bug. The SZZ algorithm~\cite{szz2005}, proposed in 2005 by Śliwerski, Zimmermann, and Zeller, performs this task. SZZ starts by identifying all modified lines in a bug-fixing commit using the diff utility. More specifically, it focuses on the lines that were deleted during the fix. It then scans the version history to locate the commit where those deleted lines were originally introduced. If this earlier commit predates the bug report, it is marked as a bug-inducing commit.


The fundamental assumption behind SZZ is that bugs are introduced in the same lines that are later modified to fix them. Subsequent studies have highlighted the limitations of this approach. Not all bugs originate from a direct code change, and SZZ can misidentify bug-inducing commits due to sources of noise, such as non-code changes (e.g., comments, renames) or broad refactorings. For example, Neto et al.~\cite{neto2018impact} found that nearly 19.9\% of lines deleted during bug fixes were due to refactorings, making their associated bug-inducing commits false positives.


To address these shortcomings, several SZZ variants have emerged. AG-SZZ~\cite{kim2006automatic} uses annotation graphs to filter out non-semantic changes like blank lines and indentation. MA-SZZ~\cite{da2016framework} targets noise introduced by meta-changes such as merging and branching. RA-SZZ~\cite{neto2018impact} focuses on removing the effects of refactorings. Among these, RA-SZZ has been shown to produce the cleanest and most accurate results. 

SZZ and its variants have been instrumental in producing datasets for software defect prediction research. The technical debt dataset~\cite{TDD} is another prominent example created by an SZZ-based implementation. Nevertheless, SZZ-based approaches have several limitations that need to be addressed e.g. accounting for bugs that become known only after a latency period~\cite{cabral2019class}, as well as bugs associated with one-line changes. The algorithm depends on explicitly labeled bug-fix commits, typically identified through references to issue tickets or keywords in commit messages. This biases the algorithm towards capturing high-visibility defects i.e., those that are severe enough to be reported, tracked, and fixed through formal channels. Yet, many low-severity, silent, or developer-noticed bugs never make it to the issue tracker and may be fixed opportunistically during unrelated work. These fixes often lack explicit labeling and are thus invisible to SZZ, resulting in an incomplete and potentially skewed view of bug-inducing changes. 
%One underexplored limitation of the SZZ algorithm is its assumption that each bug fix maps directly to a single inducing change, overlooking the possibility that some bugs emerge from the interaction of multiple commits over time. Such interaction effects, where individually harmless changes introduce faults only when combined, are difficult for SZZ to capture, as it operates on line-level annotations in isolation. This makes SZZ inherently limited in capturing the systemic or emergent nature of certain defects.

%Additionally, SZZ does not differentiate between semantic and non-semantic code changes. It treats any prior change to a line later fixed as potentially fault-inducing, even if that change had no impact on program behavior (e.g., comment edits or code reordering that preserves logic). This reliance on syntactic traceability without semantic understanding leads to false positives and reduces the reliability of fault attribution.

\subsection{Training on Within-Project or Cross-Project Data}
For projects with sufficient historical data, models are trained and evaluated using data from the same project. This approach, known as Within-Project Defect Prediction (WPDP)~\cite{turhan2009relative,basili1996}, involves using different versions or modules of the same project for training and testing. 
WPDP typically achieves higher predictive performance because it benefits from similar feature distributions between training and testing data, while its applicability can be limited in small or new projects where labeled defect data are scarce or unavailable. To address this, researchers have explored Cross-Project Defect Prediction (CPDP), where models are trained on data from other projects and then applied to the target project~\cite{zimmermann2009cross,he2012investigation}. While CPDP improves data availability and generalization potential, it introduces significant challenges such as distribution mismatch between source and target projects, making accurate prediction more difficult. To mitigate these issues, various CPDP techniques have been proposed, including data standardization, instance selection~\cite{menzies2013better}, feature mapping, and transfer learning~\cite{nam2013transfer} approaches, however, their internal details are not relevant to this thesis. 


\subsection{Just-in-Time Software Defect Prediction} 
The motivation to prevent bugs instead of just predicting them led to the idea of change-level defect prediction. Later, Kamei et al.,~\cite{kamei2012large} reframed the idea as Just-in-time software defect prediction (JIT-SDP). It is a way of predicting defects at the commit-level and helps determine whether each incremental software change is defective or not, allowing developers to preemptively detect and fix risky changes before they make it to the software repository.

JIT-SDP also improved the granularity of previously coarse-grained module level predictions. It operates at a finer granularity than release-level prediction, enabling more localized inspections. Since each change typically has a single author, triaging is simpler, and issues are addressed while design decisions are still fresh in developers' minds. Early JIT-SDP approaches~\cite{mockus2000predicting} predicted defective changes using a manually designed set of code change properties (lines added, lines deleted, code entropy) that were primarily derived from the changes themselves. Follow up works~\cite{kim2008classifying,kamei2012large} added new properties from the Version Control Systems (VCS), Issue Tracking Systems (ITS), and code review databases~\cite{kononenko2015investigating} to improve the prediction accuracy of JIT-SDP models.

Deep learning techniques achieved notable improvements in predictive performance over the aforementioned approaches. Hoang et al~\cite{hoang2019deepjit} developed end‑to‑end deep learning framework for JIT-SDP that automatically learns features from both commit messages and code changes, rather than relying on manually engineered metrics. Later, they introduced CC2Vec which uses pre-trained embeddings to capture the semantic intent of the code changes improving JIT-SDP performance.  

\subsection{Validation/Evaluation Methodology}
K-fold cross-validation method is often used to evaluate machine learning models. It splits data into 
equal-sized subsets or folds. The model is trained \textit{k} 
times, each time using \textit{k-1}
folds for training and one distinct fold for validation, ensuring every data point is used for both training and validation. Such an evaluation involves shuffling of data which disrupts the temporal ordering leading to \textit{time travel} i.e. using information that is not known at a point in time. Rakha et al.~\cite{rakha2018} refer to such an evaluation as ``classical evaluation" and claim that it unrealistically boosts performance.
 

Cabral et al.~\cite{cabral2019class} further observed that JIT-SDP models are often evaluated unrealistically because labeled training examples typically arrive with delay. This delay between the arrival of a software change and the time when its defect status becomes known is called \textit{verification latency}. Assuming defect labels that would not yet be available at the time of a commit can lead to overly optimistic results in JIT-SDP scenario. To address this issue, Cabral et al.~\cite{cabral2019class} proposed a more realistic evaluation framework based on \textit{online learning} that accounts for verification latency and processes training examples in temporal order, allowing models to incorporate newly verified data without retraining from scratch. This methodology was adopted for the evaluation of IRJIT in Chapter~\ref{chp:irjit}.

\subsection{Online Learning} 
Online learning is a machine learning approach in which models are updated incrementally as new data becomes available. Unlike traditional batch learning, where a model is trained once on a fixed dataset, online learning continuously incorporates new observations~\cite{cabral2019class}. Therefore, online learning is particularly suitable for software engineering tasks where data arrives as a stream of training examples, such as in JIT-SDP. By updating the model with new commits, online learning can adapt to changing development patterns without requiring complete retraining.

Strict online learning~\cite{cabral2023investigation} involves processing each training example only once, thus updating the classifier without retraining on past examples. This approach is useful when retraining on all historical data is computationally expensive, such as in very large or high-frequency data streams.

Online learning provides a natural way to address temporal instability in defect prediction models by allowing models to evolve together with the software project. The models in this thesis are therefore designed to support incremental updates and explicitly account for verification latency during training. 

As an alternative, offline learning models can be periodically rebuilt from scratch whenever a new training set becomes available. Although the training process ignores the time order of examples within each training set, it still respects the time order of commits and ensure JIT-SDP models are only trained on the data available at a given point in time. In this way, offline learning can approximate the JIT-SDP online scenario while allowing the use of traditional batch learning methods. In JIT-SDP, the software changes typically do not arrive at extremely high frequency, therefore strict online learning~\cite{cabral2023investigation} may not always be necessary. In such settings, periodic offline retraining may still be practical.

%\textcolor{red}{Should I add this paragraph here in the background section?}The work in this thesis follows an online setting where temporal constraints are respected and new data is incorporated sequentially. The approach is based on information retrieval rather than traditional machine learning. Instead of updating model parameters, the system incrementally updates the underlying index as new data becomes available. Therefore, the approach is better described as incremental or online retrieval rather than online learning.

\subsection{Fine-grained SDP}
While JIT-SDP models provide more granular predictions than traditional module-level models by assessing the defectiveness of individual commits, developers still need to review entire commits' changes to identify bugs, which can require significant effort. To address this challenge, line-level prediction models were introduced as a finer-grained enhancement to file-level~\cite{wattanakriengkrai2020predicting} and commit-level~\cite{yan2020JIT, pornprasit2021jitline} models. Yan et al.~\cite{yan2020JIT} designed a two-phase framework that first identifies the buggy changes. Then for each identified buggy change, it scores and ranks the line by riskiness which is estimated using an n-gram model. 
JITLine~\cite{pornprasit2021jitline} combines expert and semantic features extracted from code changes and applies a model-agnostic technique, LIME, to rank lines according to their contribution to the commit level prediction. JITFine~\cite{jitfine} extends this by using a pre-trained language model CodeBERT on the same features, and learns to identify defect‑inducing commits and locate their defective lines, achieving improved performance

By ranking lines according to their contribution to the prediction, these approaches help developers focus effort on the highest‑risk code segments, reducing developer effort and improving debugging efficiency. Chapter~\ref{chp:irjit} proposes a fine-grained SDP model and compares it against prior work~\cite{yan2020JIT, pornprasit2021jitline} mentioned in this subsection.

\subsection{Common Limitations of SDP Models}
The field of SDP faces several practical challenges despite extensive research. Traditional metrics-based models produce high false positives~\cite{clever} which can lead to wasted developer effort when inspecting modules that are ultimately non-defective. To address this limitation, later work introduced a post-processing step to confirm or refute the predictions made by metric-based models. For instance, Nayrolles et al.,~\cite{clever} proposed a two phase framework called Clever which uses code clone detection to compare predicted buggy components against historical buggy patterns. Similarly, Yan et al.,~\cite{yan2020JIT} adopted a related methodology, but instead used n-gram representations to model buggy code patterns and validate initial predictions.

Class imbalance is another prominent issue in SDP. Defect datasets are imbalanced in nature, containing very few buggy modules than the clean ones. This imbalance negatively impacts the performance of predictive models, motivating the exploration of balancing techniques\cite{tantithamthavorn2018impact} and ensemble methods\cite{laradji2015software} as strategies to deal with the skewed nature of data. Undersampling the majority class or oversampling the minority are common ways to handle data imbalance. SMOTE (Synthetic Minority Over-sampling Technique)~\cite{chawla2002smote} is another widely adopted method, which balances datasets by generating synthetic examples of the minority class through interpolation. Research~\cite{feng2021investigation} shows that SMOTE enables classifiers to better learn from limited but critical data, such as defective modules.

Another important concern in SDP is the lack of explainability~\cite{dam2018explainable, ribeiro2016should} of models. Techniques like SMOTE, while effective for data balancing, can obscure the relationship between a prediction and the original data, making it difficult to establish traceability. More broadly, ML and DL models used in defect prediction are often opaque. In particular, models that rely on learned representations, such as embeddings from deep architectures, are difficult to interpret~\cite{allamanis2014learning}. Oftentimes, developers cannot understand what individual dimensions represent or why a particular prediction was made. This lack of transparency reduces trust, and ultimately hinders the practical adoption of defect prediction tools. Addressing this challenge requires approaches that provide meaningful explanations for model predictions which is the key objective of explainability research discussed next.


\section{Explainability in Software Engineering}
Explainability refers to the ability of a model to provide understandable and meaningful information about its predictions. In software engineering, explainable models aim to help developers understand the factors affecting predictions and support informed decision-making during development and maintenance activities~\cite{dam2018explainable}. For instance, a developer using a JIT-SDP model not only wants to know if a change is risky, but also wants to understand the reasons behind the prediction~\cite{jiarpakdee2020empirical}. A model that is transparent about its reasoning builds developers' trust in its predictions which makes its adoption more likely in real-world settings~\cite{grattan2024need}.

One early approach to explainability is through rule-based tools such as FindBugs (now SpotBugs\footnote{https://spotbugs.github.io/}~\cite{hovemeyer2004finding}), and PMD\footnote{https://pmd.github.io/}. These tools provide basic reasoning by showing the code patterns that trigger their rules when detecting bugs, code smells, or vulnerabilities. One drawback of rule-based tools is that they often produce false positives and overwhelm the developers with warnings that are not always meaningful or problematic~\cite{johnson2013don}. 
Developers may also disregard flagged violations because insufficient context makes it difficult to assess their relevance, thereby limiting the practical utility of such tools during debugging or maintenance tasks. 

Machine learning approaches offer a more accurate alternative than rule-based tools, but they operate as black boxes, leaving the developers uncertain about why a particular prediction was made. 
Surveys of practitioners show that few SDP studies provide explanations, even though explanations are important for developer adoption~\cite{jiarpakdee2021practitioners}. A key challenge, therefore, is to design models that combine predictive power with explainability.


Explainability in ML can be categorized into global and local explanations~\cite{menzies2011local}. Global explanations summarize the overall behavior of a model across all inputs by relating independent variables to outcomes. For example, decision trees expose their structure explicitly, whereas techniques such as variable importance analysis in Random Forests provide insights into influential features. These explanations are useful for understanding model behavior at a high level, but can't explain individual predictions.
Local (or instance-level) explanations~\cite{jiarpakdee2020empirical}, in contrast, focus on a specific instance such as why a particular file, commit, or line is predicted as defective. These explanations help developers act on specific predictions and guide decisions about debugging, testing, or code changes.

\subsection{Model-Agnostic Local Explanation Techniques}
Local explanations can be generated using model-agnostic techniques like LIME~\cite{ribeiro2016should}, SHAP~\cite{lundberg2017unified}, which  approximate the complex model locally by replacing it with a simpler, interpretable model such as a linear model or decision tree.

To build a local model, LIME (Local Interpretable Model-agnostic Explanations)~\cite{ribeiro2016should} uses perturbation. It is a process that generates ``synthetic neighbors" around the instance to be explained by observing its effect on the model's prediction. For example, it may slightly modify the feature values of the input instance to generate synthetic instances. LIME then trains a simple, interpretable model (e.g., a sparse linear regression classifier) on the newly synthesized instances to approximate the complex model's behavior in the neighborhood of the input. The resulting coefficients of the model serve as explanations highlighting which features had the greatest influence on that specific prediction.

%shap uses game theory to calculate the contribution probability of each feature to the final prediction of the prediction mode
SHAP (SHapley Additive exPlanations)~\cite{lundberg2017unified} is another model-agnostic technique grounded in game theory. It computes the contribution of each feature to the prediction based on Shapley values. SHAP provides consistent explanations in comparison with LIME, but it is often more computationally intensive~\footnote{https://apxml.com/posts/lime-vs-shap-difference-interpretability}.
Both methods have been successfully applied in SE. For example, Jiarpakdee et al.~\cite{jiarpakdee2021practitioners} found LIME effective in explaining file-level defect predictions, while Pornprasit et al.~\cite{pornprasit2021jitline} used it to identify risky lines (i.e., those containing risky tokens) within buggy commits. To further improve the use of explanations in defect prediction, Pornprasit et al.~\cite{pornprasit2021pyexplainer} proposed PyExplainer, a rule-based, model-agnostic technique that generates human-readable, actionable insights. PyExplainer produces synthetic neighbors that are more similar leading to more accurate local models. As a result, its explanations for JIT-SDP models were found to be more unique and consistent than that of LIME.




In my thesis, we built upon these ideas and design an explainable approach for JIT-SDP that is presented later in Chapter~\ref{chp:irjit}. Similar to model-agnostic local explanation techniques, the goal is to provide insights into why a given commit was predicted as buggy rather than treating the prediction as a black-box decision. Instead of relying on feature perturbations or local models, my approach uses IR techniques to identify commits similar to a given commit. These similar commits provide concrete examples that explain the prediction and help developers understand why the commit may be risky. Furthermore, the proposed approach identifies the top defective lines within a predicted buggy commit, providing additional guidance for debugging. These explanations make the proposed JIT-SDP approach more transparent by design rather than explained after the fact, and facilitate debugging, triaging, and long-term software maintenance.
